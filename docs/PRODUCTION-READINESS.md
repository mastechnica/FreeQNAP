# Production readiness and acceptance order

Reviewed 30 October 2026. This is an acceptance plan, **not production sign-off**. It separates working source and file-backed tests from physical data protection. The initial audit was read-only. Subsequent owner-approved commissioning and its remaining limits are recorded below.

## Fresh observations

- The second unit runs the installed 6.12.114 FreeQNAP1 kernel. Both OS mirror members are present and synchronized; no systemd service is failed. Broker, console, fixed full cooling, internal SMART monitoring and the network controller are active.
- The owner-approved four-disk RAID5 now provides two mounted ext4 data volumes, about 14.97 TB each after filesystem overhead. Both passed bounded fsynced write/direct-read hashes, followed by a real-filesystem file/archive/media and Restic restore campaign with modes/ACLs/xattrs and no live overwrite. The temporary files/repository were cleaned; permanent shares and backup destinations were not configured. Initial RAID synchronization is still running; disk-failure protection and production storage acceptance are not complete. Shares, NAS users, backup repositories and media libraries remain unconfigured.
- The owner initialized the separate console administrator privately. HTTP is bound to loopback for SSH forwarding; a private-CA LAN HTTPS endpoint is deployed and passed a certificate-verified response check. Owner installation of the public CA/browser trust remains pending; see [local HTTPS](LOCAL-HTTPS.md).
- After the owner restored upstream access, verified outbound HTTPS and direct signed Debian main/updates/security metadata refresh passed; no package upgrades were pending. Chrony acquired a valid stratum-2 reference with normal leap status; a later check showed about 1.2 ms system offset and 3.4 ms root dispersion. Long-term time-source availability still belongs in soak acceptance. No router change was made by FreeQNAP.
- Local durable health alerts now cover RAID, SATA SMART availability/failure, capacity, CPU temperature, backups, worker/services, configured HTTPS, DDNS and notification failures. Optional SMTP settings and installable PWA/Web Push are deployed but disabled. Real owner inbox/device receipt remains unverified. The native test used isolated local servers and crypto fixtures; no owner message was sent. See [health and notifications](HEALTH-NOTIFICATIONS.md).
- The TR-004 remains read-only and its requested external volumes do not exist. The reproduced first-write controller failure now passes bounded tests after an exact-board EJ188 PCIe MRRS workaround; normal-kernel reboot, flash-drive random write/readback and three enclosure offsets passed. Formatting, sustained soak and reconnect/power-loss acceptance remain separate; see the USB report.
- The current native ARMhf application suite passed 192 tests; six Node desktop/PWA checks and isolated real SMTP/DDNS/TLS campaigns passed. Optional DDNS has sixteen provider profiles and no configured/enabled account. Browser install/permission, live-provider interoperability and actual notification receipt remain owner tests; see [DDNS](DYNAMIC-DNS.md). The installer has 43 tests, including known-identity/configuration checks against the prepared bootstrap and actual embedded CPIO. The existing uninstalled candidate passed both audits; these checks do not prove arbitrary binaries secret-free or authentic. These do not replace physical storage, client, failure/rebuild or disaster-recovery acceptance.
- Upstream released **6.12.115 on 30 October 2026**. The running base remains 6.12.114; a separate newer candidate has compiled and passed image/module checks but has not been RAM-booted. No claim of current kernel patch level or complete CVE/board-driver applicability is made. See [kernel maintenance](KERNEL-SECURITY.md).

## Feature-specific acceptance

Enable only the features needed for the chosen deployment; leave the others disabled or explicitly unaccepted.

- **Encrypted foreign USB:** physical password/key unlock, safe lock/eject, reconnect and failed-password tests. LUKS/ext4 and LUKS/NTFS file-backed workflows passed; software-encrypted APFS passed a known-file fixture. BitLocker/To Go crypto vectors matched known decrypted hashes, but their NTFS metadata did not mount; complete BitLocker browsing still needs a clean filesystem test. No universal-format or hardware-bound Mac encryption claim.
- **Media/DLNA:** actual chosen Apple TV/Roku/Fire TV/TV players, approved-client playback and revoked/unapproved denial, scanner/scraper error handling, and ARMhf resource/codec limits. Browser-native playback is not a transcoding service.
- **VPN/private LAN:** actual provider/client and physical LAN client tests, reboot/tunnel-loss kill switches, DNS leak checks, management continuity, firewall rules and DHCP separation. Private LAN is currently disabled. Namespace tests are useful evidence, not physical gateway commissioning.
- **Downloads/torrents:** real intended servers/peers, resume after network/process/boot interruption, disk-full and path/permission behavior, integrity and resource limits.
- **10GbE, SuperSpeed, adaptive cooling, watchdog expiry and wake:** separate physical acceptance before advertising or depending on each feature. Existing gigabit operation and fixed full cooling can remain the adopted baseline.

## Private use versus public release

A private installed NAS need not wait for a polished public installer once its adopted functions pass the operational gates. A public turnkey release additionally needs a clean pinned build, complete dependency/corresponding-source/license inventory, signed immutable artifacts, interruption-safe guided install/recovery and independent repeat installation acceptance. Current source remains local and unpublished pending owner review.

Full-chip/SPI bootloader restoration remains **excluded by owner decision**, not silently accepted or added back to this plan. Retain verified private original backups and the tested UART/TFTP RAM rescue path, with the residual bootloader-failure limitation stated clearly.

## Suggested execution order

Finish initial internal RAID synchronization, then test post-write shutdown/cold boot, RAM-only kernel/recovery changes and controlled failure/rebuild/backup/restore. Complete trusted client administration, clock quality, alert receipt, real-client operations and soak acceptance. Continue USB transport work separately. Establish a supported internal-only baseline separately if the external enclosure remains blocked. Only then move important data, retaining an independent verified backup throughout.
